# Move earthaccess repository to independent organization

## Status
Accepted

## Date
2026-04-14

## Deciders
Not discussed.

## Context and Problem Statement
The earthaccess project is community-owned, and a proposal was made to reflect this by transferring or forking the repository to an independent organization with shared ownership among interested individuals and organizations. The current repository is hosted under the NSIDC organization. The community had been considering this move for over a year. The goal is to insulate the project from host-organization directives and to group related efforts collectively under a neutral umbrella. Without this transition, the project remains dependent on NSIDC policies and could face future disputes or fragmentation.

## Decision Drivers
* Community ownership and neutrality.
* Preserving commit history, issues, and discussions.
* Automatic redirects from the old location to the new one.
* Avoiding disruption to users and contributors.
* Ability to group related projects under a single organization.
* Long-term sustainability and collaboration.

## Considered Options
* Transfer the repository to an independent organization (e.g., earthaccess-dev).
* Fork the repository to a new organization, potentially with a name change.
* Join an existing open-source organization (pangeo‑data, cloudnativegeo, NASA Openscapes).
* Integrate with or pivot to the EODAG project by developing plugins or adopting it as a backend.

## Decision Outcome
Move the earthaccess repository from NSIDC to the earthaccess‑dev GitHub organization. This decision is documented at https://github.com/earthaccess-dev/earthaccess/blob/main/docs/governance/decisions/929-move-repository.md.

## Consequences
* All repository history, issues, and pull requests are preserved; GitHub automatically redirects from the old URL to the new one.
* A new independent governance structure under earthaccess‑dev provides community ownership and reduces exposure to external organizational changes.
* The move required buy‑in from NSIDC, which was obtained.
* [Inferred] Maintainers and contributors now operate under the earthaccess‑dev organization’s permissions and policies.
* [Inferred] Future decisions about the project’s development will be made by the earthaccess‑dev community.

## Pros and Cons of the Options
### Transfer to independent org (chosen)
* Pro: Preserves all history, issues, and discussions.
* Pro: Automatic GitHub redirects minimize user disruption.
* Pro: Low transition cost compared to forking.
* Pro: Enables grouping of related tools (e.g., python_cmr) under one roof.
* Con: Requires host organization (NSIDC) consent.

### Fork to independent org
* Pro: Clean break, no reliance on NSIDC.
* Pro: Full control over name and new identity.
* Con: Loss of issue/PR history, no redirects, high disruption.
* Con: Significant effort and cost to recreate project infrastructure.

### Join an existing organization
* Pro: Access to established governance and community.
* Pro: Potential collaboration with other projects.
* Con: Some orgs (e.g., NASA Openscapes) have had restrictive CoC changes imposed externally.
* Con: Pangeo governance was described as “pretty bare‑bones” and may not provide strong protection.

### Pivot to EODAG
* Pro: EODAG has existing plugin architecture for data providers, which could be extended.
* Pro: Wider development community and already solved problems.
* Con: Disruptive to current user base and requires significant rework.
* Con: EODAG is oriented toward imagery; earthaccess covers broader data types.

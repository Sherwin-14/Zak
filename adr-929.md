# Move or fork to independent organization

## Status
Accepted

## Date
2026-04-14

## Deciders
Steering Council

## Context and Problem Statement
The earthaccess project is community‑owned but hosted under NSIDC. The community wants to reflect this ownership by moving the repository to an independent organization where ownership can be shared among interested individuals and organizations. Failing to do so would keep the project under a single institutional umbrella, limiting community governance and independence.

## Decision Drivers
* Community ownership and governance independence from the current host (NSIDC)
* Avoiding disruption to users and contributors
* Preserving issue history, pull requests, discussions, and GitHub stars
* Enabling easier grouping of related community‑owned tools (e.g., python_cmr)
* Long‑term sustainability of the project as a shared community resource

## Considered Options
* Move (transfer) the repository to a new independent organization
* Fork the repository to a new independent organization
* Join an existing community organization (e.g., pangea‑data, openscapes)

## Decision Outcome
The repository will be moved (transferred) to the new independent GitHub organization `earthaccess-dev`. Transferring keeps the full project history, provides automatic URL redirects, and minimizes community disruption compared to a fork. Joining an existing organization was declined because of past governance impositions observed in similar orgs.

## Consequences
* Easier: Users and tools referencing the old NSIDC URL will be automatically redirected to `earthaccess-dev/earthaccess`. All issues, pull requests, and discussions are preserved without migration work.
* Easier: The project can group other community‑owned tools under the same organization, improving consistency and cross‑linking.
* More difficult: Transfer requires buy‑in from NSIDC and a coordinating agreement; it cannot be accomplished unilaterally. But the completed status of this decision indicates that agreement has been reached.
* [Inferred] The project will need to update all references in documentation, CI configuration, and external sites to the new organization name.
* Potential risk: If a dispute over the name *earthaccess* arises later, the project may face legal or branding complications, though the name is not a NASA trademark.

## Pros and Cons of the Options

### Move (transfer)
* Pros: Preserves all history and stars; adds automatic URL redirects; requires minimal community re‑onboarding; no name change necessary.
* Cons: Requires cooperation from the current host organization; may inherit existing permission artifacts.

### Fork
* Pros: Can be done unilaterally without host approval; provides a clean break.
* Cons: Loses issues, pull requests, discussions, and stars; would be highly disruptive; entails significant re‑work to rebuild community and tooling; losing the GitHub redirect may fragment users.

### Join existing organization
* Pros: Immediate access to an established community and governance; potential for broader collaboration.
* Cons: Governance may be constrained by the parent organization’s policies; observed cases (e.g., openscapes) where external CoC changes were imposed without project consent.

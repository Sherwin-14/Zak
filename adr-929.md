# Move repository to independent organization

## Status
Accepted

## Date
2026-04-14

## Deciders
earthaccess steering committee

## Context and Problem Statement
The earthaccess project was hosted under a NASA-affiliated organization (NSIDC). The project is community-owned, and there was a desire to reflect that ownership by moving to an independent organization. A code of conduct change was imposed externally (related issue #928), highlighting the need for independence. Without a transfer, the project could face unilateral changes and lack of community governance. Additionally, maintainers had been considering a move for over a year for broader reasons.

## Decision Drivers
* Moving (transferring) keeps issues, discussions, and automatically redirects the old URL to the new org—forking loses these benefits.
* Forking, especially with a name change, would be disruptive and costly to recover current functionality.
* A transfer requires buy-in from the current host (NSIDC); if not possible, forking would be a last resort.
* An independent org allows grouping of related projects (e.g., python_cmr) under consistent practices and shared documentation.
* The project name is not a NASA brand, so there is no legal barrier to a move.
* Joining an existing org (pangeo-data, cloudnativegeo) was considered but a dedicated org was preferred to maintain independence.

## Considered Options
* Fork the repository to a new independent organization (e.g., earth-observation-community, earthaccess-contrib)
* Transfer (move) the repository to a neutral, independent organization
* Join an existing community organization such as pangeo-data or cloudnativegeo
* Pivot to using EODAG as a backend (parallel exploration, not a direct repo decision)

## Decision Outcome
Transfer (move) the repository to the newly created independent organization `earthaccess-dev` (https://github.com/earthaccess-dev/earthaccess). This preserves the full project history, issues, discussions, and provides automatic redirects from the old URL.

## Consequences
* Easier transition: All issues, discussions, and contributions are retained, and old links redirect automatically.
* Less disruption to users and contributors compared to a fork.
* Independent governance and community ownership are established, insulating the project from future unilateral external changes.
* Requires agreement from NSIDC; such agreement was secured before the transfer.
* Enables central documentation and consistent development practices across sister projects (e.g., python_cmr).
* [Inferred] Existing URLs and references to the old repository remain functional via redirects, reducing broken links.

## Pros and Cons of the Options
### Fork to a new independent org
* Good, because it provides a clean break and avoids any future ownership disputes with the old host.
* Bad, because it loses all issues, discussions, and contributions; community disruption is high; costs include rebuilding momentum and fixing broken references.

### Transfer (move) to a neutral org
* Good, because it preserves everything, includes automatic redirects, and minimizes disruption.
* Bad, because it requires cooperation from the current host organization (NSIDC). If denied, the community may be stuck.

### Join an existing org (e.g., pangeo-data)
* Good, because it offers an established namespace, potential broader exposure, and existing governance.
* Bad, because the existing org’s policies may still allow external influences (e.g., a past incident with NASA Openscapes). Also, earthaccess would share an org with other projects, potentially diluting focus.

### Explore EODAG integration
* Good, because EODAG already has plugins for discovery and download, and cooperation could broaden the development community.
* Bad, because full migration would be highly disruptive; earthaccess provides specific CMR/DAAC knowledge that is not easily replaced.

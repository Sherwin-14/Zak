# Move earthaccess repository to independent organization

## Prologue
The earthaccess project is community-owned but was hosted under the NSIDC GitHub organization. The community wished to reflect that ownership by moving the repository to a neutral, independent organization not controlled by any single institution. Without a move, the project would remain under the host’s governance, potentially exposing the community to external directives and disruption of collaborative work.

## Discussion
Participants evaluated two main paths: transferring (“moving”) the repository to a new organization or forking. A transfer was preferred because it preserves all issues, pull requests, discussions, and automatically redirects visitors from the old location, minimizing user disruption. Forking, especially with a name change, was seen as a last resort due to the effort and cost needed to regain the current community standing.

Several potential homes were proposed, including joining existing organizations like pangeo-data or cloudnativegeo, or creating a new organization. The name `earthaccess-dev` was created and favored. The community also examined EODAG as a complementary framework and discussed building plugins for NASA data rather than replacing earthaccess entirely. The steering committee was asked to decide between move and fork, and ultimately resolved to move.

## Solution
Move the earthaccess repository to the independent GitHub organization earthaccess-dev. The decision is recorded in the repository’s governance document: `https://github.com/earthaccess-dev/earthaccess/blob/main/docs/governance/decisions/929-move-repository.md`.

## Consequences
- The repository becomes free of NSIDC institutional control.
- All existing issues, pull requests, discussions, and history are retained.
- Automatic redirects from the original NSIDC location protect discoverability.
- The move may require NSIDC’s cooperation; absent that, a fork would be the fallback.
- The new org can host related community tools (e.g., python_cmr) under consistent practices and unified documentation.
- [Inferred] EODAG plugin development can continue in parallel without altering the core earthaccess codebase.
- References and documentation must be updated to point to the new organization.

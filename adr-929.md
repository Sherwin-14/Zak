# Move or fork to independent organization

## Status
Accepted

## Date
2026-04-14

## Deciders
Steering committee

## Context and Problem Statement
The earthaccess project is community-owned and developed, but its repository was hosted under the NSIDC GitHub organization. This arrangement gave a single institution control over the repository, which conflicted with the project’s community-oriented nature and raised concerns about the ability to protect the project from unilateral changes — such as the Code of Conduct alteration discussed in issue #928.

The community wanted to move the repository to an independent, neutral organization where ownership and governance could be shared among contributors and stakeholders. The primary question was whether to fork the repository (creating a separate copy) or transfer it (moving the existing repository) to a new organization, and which organization to choose.

Not addressing this would leave the project under institutional control, risking future disruptions, disputes over the name, and fragmentation of the community if a forced or later fork became necessary.

## Decision Drivers
- Preserving the project’s issue history, discussions, and community records.
- Avoiding disruption and significant transition effort for the user community.
- Establishing a governance model that insulates the project from single-org directives.
- Maintaining the collaborative knowledge space around CMR and DAAC operations.
- Enabling group development practices for earthaccess and related tools like `python_cmr`.

## Considered Options
- Fork the repository to an independent GitHub organization (e.g., `earth-observation-community`, `earthaccess-contrib`, `earthaccess-dev`).
- Transfer (move) the repository to a neutral GitHub organization (e.g., `earthaccess-dev`).

## Decision Outcome
Move the repository to the `earthaccess-dev` GitHub organization.

**Rationale:** Transfer preserves all history, issues, discussions, and stars, and provides automatic redirects from the old location, minimizing disruption. Community members and existing contributors gain shared ownership, allowing the project to continue as a community-driven effort while still benefiting from institutional contributions. This option was feasible because NSIDC and ESDIS were willing to consent to the transfer.

## Consequences
- The transfer provides automatic GitHub redirects from `NSIDC/earthaccess` to `earthaccess-dev/earthaccess`, so any incoming links continue to work.
- All issues, pull requests, discussions, and commit history are preserved intact — no re-creation of issues or lost context.
- The project now has shared ownership among community members, insulating it from unilateral organizational policy changes.
- [Inferred] The move required explicit buy-in from NSIDC; the relationship with NASA ESDIS was discussed, and future NASA funding opportunities may be influenced by the new independent status.
- The new organization allows co-locating related tools like `python_cmr` and aligning development practices under a single governance framework.

## Pros and Cons of the Options
### Move
- Pros: Retains all history, issues, discussions, and stars; automatic redirects eliminate link rot; minimal community disruption; keeps institutional contributions visible; allows future co-housing of related projects.
- Cons: Requires host organization approval; existing CI/CD and permission configurations may need updates.

### Fork
- Pros: Can proceed immediately without any outside consent; provides a completely clean break from the original host.
- Cons: Loses all history, issues, and discussion threads; no automatic redirect — users and hyperlinks break; massive manual transition effort; risk of community fragmentation and name disputes.
